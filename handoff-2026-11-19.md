## 1. What this project is

`krdbg` is a target-agnostic, linked-in debugger surface for KR virtual machines:
one C++20 UI (`krdbg_ui`) over a neutral session model (`krdbg_core`), with
per-VM adapters and KDBG as the debug format. Windows uses a Win32 GDI presenter
with no `SDL2.dll`; Linux x64 and ARM64 use SDL2.

The design is in [PLAN.md](PLAN.md); the actionable milestone/task/gate plan is
[implementation.md](implementation.md). `PLAN.md` wins if they disagree.

## 6. Architecture summary

- **`IDebugTarget`** wraps one VM: state groups, contexts, step/run, memory,
  disassembly, unwind, `IComPort`, `IVideoSource`.
- **`DebugSession`** owns the target, `DebugInfo`, breakpoints, selected context,
  stepping, call stack, variables and statistics.
- **`DebugInfo`** is a neutral model; `krdbg_kdbg` alone translates
  `KdbgImage` into it.
- **The UI contains no VM types, register numbers, instruction widths, address
  widths, or `if (target == …)`.** VM-specific code lives in an adapter.
- **COM port** is a three-register byte port (`OUT`, `IN`, `STATUS` with
  `RX_READY`, `TX_READY`, `OVERRUN`), not a UART and not the framebuffer console.
- **SCREEN/VIDEO** is a raw framebuffer. The video window and the bottom-right
  `VIDEO` preview are views; a guest cell console is just pixels.
- **Settings** are schema-driven: VM/compiler/linker/assembler providers publish
  labels, descriptions, types, ranges, defaults and current values; JSON is the
  template/persistence/external-tool format. User settings in the home config
  dir, sparse project overlay at `<project>/.krdbg/settings.json`.
- **Statistics** are first-class: `instr`, execution-only `time`, `ips`, and
  `CLR`; target supplies a monotonic instruction count.
- **Toolbar** is `RUN RESET LOAD KERNEL` plus stats/`CLR`/`VIDEO`/gear; no
  top-level step, breakpoint or Build buttons.

Read `PLAN.md` §4 and §6 for the full contracts.

## 10. Known traps / risks

- **No product code yet.** The repo is documentation only. Do not describe
  `krdbg` as built or tested.
- **No build commands.** M0.1 creates CMake and presets; M0.9 records the real
  commands. Do not claim a build until it runs.
- **KDBG v1 is limited.** It has no register locations, base classes, array
  element types, scopes or 64-bit addresses. KR32's current UI shows
  register-held locals; full parity needs KDBG v1.1, which is KRCompiler work.
- **KR16 `.kex` loses KDBG.** KRCompiler's writer emits only `.text` and
  `.debug_str`. KR16 must use legacy debug info until that changes.
- **`krc::debug` does not exist as a package.** The vendored pair is temporary
  and must carry provenance and a parity test against
  `krc --dump-symbols --json`.
- **No ARM64 runner.** G0 and G6 cannot pass until the Raspberry Pi runner is
  registered and labeled.
- **No CI workflow yet.** M0.8 creates it; GitHub Actions is assumed.
- **Scope:** do not write in `kr32`, `KR16` or `KRCompiler`; do not build them in
  their trees. Reading and using prebuilt binaries is allowed.
- **Golden hashes:** Windows/Linux x64 must match; ARM64 may differ. Do not
  silently regenerate a hash to make a gate pass.
- **No secrets:** credentials are host-managed; keep them out of commands,
  files, logs and commits.
